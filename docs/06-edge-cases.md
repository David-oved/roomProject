לכל מקרה: מה קורה, מה ההחלטה, ואיפה בקוד זה נאכף.

## א. סינכרון ותחרות (Concurrency)

### ⭐ 1. שני משתמשים כותבים בו-זמנית

**המצב:** A ו-B לוחצים "אני קונה את זה" על אותו מוצר, בהפרש של 200ms.

**מה קורה בפועל:** Firebase מיישם Last-Write-Wins. הכתיבה השנייה דורסת. `assignedTo` יהיה של B, ו-A לא יידע שנדרס.

**❌ למה "Firebase מטפל בזה" היא תשובה לא מספקת:** LWW מונע שחיתות נתונים, אבל לא מונע ש**שני אנשים יקנו את אותו חלב**. הבעיה כאן היא של המשתמש, לא של בסיס הנתונים.

**✅ ההחלטה: `runTransaction` על תפיסת פריט.**

```ts
// src/services/itemService.ts
export async function claimItem(roomCode: string, itemId: string, userId: string) {
  assertOnline('לתפוס מוצר');

  const itemRef = ref(db, `rooms/${roomCode}/items/${itemId}`);
  const result = await runTransaction(itemRef, (item: Item | null) => {
    if (!item) return;                          // נמחק בינתיים — ביטול
    if (item.status !== 'needed') return;       // מישהו הקדים — ביטול
    return { ...item, status: 'buying', assignedTo: userId };
  });

  if (!result.committed) {
    const current = result.snapshot.val() as Item | null;
    if (!current) throw new Error('המוצר נמחק בינתיים');
    throw new Error(`${current.assignedTo === userId ? 'כבר תפסת' : 'מישהו אחר כבר תפס'} את המוצר הזה`);
  }
}
```

התוצאה: A מקבל הודעה ברורה *"יוסי כבר תפס את המוצר הזה"* במקום לגלות את זה בסופר.

**איפה עוד transaction חובה:** יצירת חדר (שם ייחודי), אישור קנייה (מניעת אישור כפול).
**איפה LWW מספיק:** עריכת הערות, שינוי עדיפות, שינוי תיאור חדר.

### 2. המנהל מאשר את אותה קנייה פעמיים

**המצב:** לחיצה כפולה על "אשר", או שני מכשירים של המנהל.

**הסיכון:** המאזנים מתעדכנים פעמיים. החוב מוכפל.

**✅ ההחלטה:** transaction שבודקת שהסטטוס עדיין `pending`, בשילוב חישוב המאזנים מהיומן ולא בהצטברות.

```ts
const result = await runTransaction(purchaseRef, (p: Purchase | null) => {
  if (!p) return;
  if (p.status !== 'pending') return;   // כבר טופל
  return { ...p, status: 'approved', approvedBy: adminId };
});
if (!result.committed) throw new Error('הקנייה כבר טופלה');
```

> **ההגנה האמיתית:** המאזנים **נגזרים מיומן הקניות** ולא מצטברים. גם אם `approved` נכתב פעמיים, `computeBalances()` סופרת את הקנייה **פעם אחת**. זו הסיבה המרכזית לבחירה במאזנים נגזרים.

### 4. התנגשות קוד חדר

**הסיכוי:** 32⁶ = 1.07 מיליארד קודים. עם 10,000 חדרים — כ-1 ל-100,000.

**✅ ההחלטה:** לולאת 5 ניסיונות עם בדיקה מול `roomCodes/`. אחרי 5 כישלונות — שגיאה ידידותית. הסיכוי לכך זניח (≈10⁻²⁵).

## ב. רשת ואופליין

### ⭐ 5. משתמש מנסה לפעול ללא אינטרנט

**✅ ההחלטה: אופליין = קריאה בלבד.** [מפורט במלואו ב-05](./05-offline-pwa.md).

- הכפתור **מושבת ונראה מושבת**, לא לחיץ-ואז-שגיאה
- `assertOnline()` בכל service — רשת ביטחון אם כפתור נשכח
- באנר sticky שלא ניתן לסגירה
- הנתונים מוצגים מהמטמון

### 6. פתיחה ראשונה של האפליקציה ללא רשת

**המצב:** משתמש חדש, מטמון ריק, אין רשת.

**✅ ההחלטה:** מסך ייעודי, לא מסך טעינה אינסופי.

```tsx
  action={<Button onClick={() => location.reload()}>נסה שוב</Button>}
/>
```

### 7. Wi-Fi מחובר אבל אין אינטרנט (בית קפה / קמפוס)

**המצב:** `navigator.onLine === true`, אבל אין תקשורת בפועל. זה נפוץ מאוד ברשתות מעונות.

**✅ ההחלטה:** `.info/connected` הוא מקור האמת, לא `navigator.onLine`. תוך ~2 שניות המצב מזוהה נכון.

---

### 8. הרשת נופלת **באמצע** כתיבה

**המצב:** המשתמש לחץ "קניתי ₪28", והחיבור נופל תוך כדי.

**✅ ההחלטה:**
- ה-Promise של `update()` לא מתממש → מציגים ספינר על הכפתור, לא "נשמר"
- טיימאאוט של 10 שניות → *"לא הצלחנו לשמור. בדקו את החיבור ונסו שוב."*
- **הפעולה לא נשמרת בשום מקום** — המשתמש חוזר על הפעולה. עקבי עם מודל הקריאה-בלבד.

```ts
export function withTimeout<T>(p: Promise<T>, ms = 10_000): Promise<T> {
  return Promise.race([
    p,
    new Promise<T>((_, rej) =>
      setTimeout(() => rej(new Error('הפעולה ארכה זמן רב מדי. בדקו את החיבור.')), ms)),
  ]);
}
```

## ג. משתמשים וחשבונות

### ⭐ 10. משתמש מוחק את חשבונו — מה קורה למוצרים ולחובות שלו?

זה מקרה הקצה החשוב ביותר במערכת, כי הוא נוגע בכסף של אנשים אחרים.

**❌ מחיקה קשה (Hard delete) אסורה.** אם מוחקים את המשתמש והקניות שלו, המאזנים של **כל שאר החברים** משתנים רטרואקטיבית. מישהו שהיה חייב ₪40 פתאום לא חייב — בלי ששילם.

**✅ ההחלטה: מחיקה רכה (Soft delete) עם משתמש רפאים.**

```ts
export async function deleteAccount(userId: string, rooms: Record<string, true>) {
  assertOnline('למחוק חשבון');

  const updates: Record<string, unknown> = {};

  for (const code of Object.keys(rooms ?? {})) {
    // המשתמש נשאר ברשימת החברים — אחרת כל הקניות שלו יאבדו את ההקשר
    updates[`rooms/${code}/members/${userId}/status`] = 'removed';
    updates[`rooms/${code}/members/${userId}/name`] = 'משתמש שנמחק';
    updates[`rooms/${code}/members/${userId}/email`] = 'deleted@removed';
    updates[`rooms/${code}/members/${userId}/avatar`] = null;
  }

  // הפרופיל האישי נמחק לגמרי — זו דרישת פרטיות
  updates[`users/${userId}`] = null;

  await update(ref(db), updates);
  await deleteUser(auth.currentUser!);   // מחיקה מ-Authentication
}
```

**מה נשמר ומה נמחק:**

| נתון | גורל | סיבה |
|------|------|------|
| פרופיל ב-`/users` | **נמחק** | פרטיות — מייל, שם, תמונה |
| רשומת חבר בחדר | נשארת, מסומנת `removed` | בלעדיה כל היומן הכספי נשבר |
| שם מוצג בחדר | הופך ל"משתמש שנמחק" | פרטיות + הקשר היסטורי נשמר |
| מוצרים שדיווח | **נשארים** | מישהו עדיין צריך לקנות אותם |
| קניות שביצע | **נשארות** | הכסף אמיתי |
| מאזן | **נשאר** | חוב לא נעלם כשמוחקים אפליקציה |

**חסימה חשובה:** משתמש עם מאזן שאינו 0 מקבל אזהרה לפני מחיקה:

> *"למאזן שלך יש יתרה של ₪34.50. אם תמחק את החשבון, החוב יישאר רשום בחדר על שם 'משתמש שנמחק'. מומלץ לסגור חשבון עם השותפים לפני המחיקה."*

**אם המשתמש הוא המנהל היחיד:** חובה להעביר ניהול או למחוק את החדר. ראו מקרה 12.

### 11. משתמש שהוסר מהחדר

**✅ ההחלטה:** `status: 'removed'` ולא מחיקה — אותו היגיון כמו מקרה 10.

- הגישה נחסמת **מיידית** ברמת ה-Rules (`status === 'active'` נדרש לקריאה)
- ההאזנות שלו מקבלות `PERMISSION_DENIED` בתוך שנייה
- ב-UI: הפניה אוטומטית לדף הבית עם ההודעה *"הוסרת מהחדר"*
- הקניות והמוצרים שלו נשארים ביומן
- אם ירצה לחזור — יגיש בקשה חדשה, שהמנהל יאשר

```tsx
// זיהוי הסרה בזמן אמת
useEffect(() => {
  if (!roomCode || !user) return;
  return onValue(ref(db, `rooms/${roomCode}/members/${user.uid}/status`), (snap) => {
    if (snap.val() !== 'active') {
      toast.warn('הוסרת מהחדר');
      navigate('/onboarding', { replace: true });
    }
  });
}, [roomCode, user]);
```

### ⭐ 12. המנהל מוחק את החדר בטעות

**❌ אין backup אוטומטי ב-RTDB** בתוכנית החינמית. מחיקה היא סופית.

**✅ ההחלטה: שלוש שכבות הגנה + ייצוא.**

**שכבה 1 — אישור בהקלדה:**

```tsx
<ConfirmDialog
  danger
  title="מחיקת החדר לצמיתות"
  body={
    <>
      <p>הפעולה הזו <b>בלתי הפיכה</b>. יימחקו:</p>
      <ul>
        <li>{itemCount} מוצרים</li>
        <li>{purchaseCount} קניות בסך {formatILS(totalSpent)}</li>
        <li>{memberCount} חברים</li>
        <li>כל היסטוריית המאזנים</li>
      </ul>
    </>
  }
  requireTyping={roomName}          // ← חייב להקליד את שם החדר
  confirmLabel="מחק את החדר לצמיתות"
/>
```

**שכבה 2 — חסימה על מאזן פתוח:**

```ts
const open = Object.values(balances).filter((b) => b !== 0);
if (open.length > 0) {
  throw new Error(
    'לא ניתן למחוק חדר עם חובות פתוחים. סגרו את החשבונות עם כל החברים תחילה.'
  );
}
```

זו ההגנה המשמעותית ביותר — היא מונעת את הנזק האמיתי (מחיקת רישום כספי), ולא רק את הלחיצה.

**שכבה 3 — ייצוא לפני מחיקה:**

```ts
export async function exportRoom(code: string): Promise<Blob> {
  const snap = await get(ref(db, `rooms/${code}`));
  return new Blob([JSON.stringify(snap.val(), null, 2)], { type: 'application/json' });
}
```

הדיאלוג מציע **"הורד גיבוי לפני המחיקה"** ומוריד קובץ JSON. לא שחזור אוטומטי, אבל הנתונים לא נעלמים.

### 13. המנהל עוזב או מוחק את עצמו

**המצב:** חדר בלי מנהל = אף אחד לא יכול לאשר קניות, לאשר חברים, או לשנות הגדרות. החדר "מת".

**✅ ההחלטה:** המנהל **לא יכול** לעזוב לפני שהוא בוחר אחת משתי אפשרויות:

```
┌──────────────────────────────────────────────────────┐
│  אתם מנהלי החדר. לפני שתעזבו, בחרו:                  │
│                                                      │
│  ○ העברת הניהול ל: [ ▼ בחרו חבר ]                    │
│  ○ מחיקת החדר כולו (יש 3 חברים נוספים)               │
└──────────────────────────────────────────────────────┘
```

```ts
export async function transferAdmin(code: string, from: string, to: string) {
  assertOnline('להעביר ניהול');
  await update(ref(db), {
    [`rooms/${code}/metadata/adminId`]: to,
    [`rooms/${code}/members/${to}/role`]: 'admin',
    [`rooms/${code}/members/${from}/role`]: 'member',
    [`roomCodes/${code}/adminId`]: to,   // ‼️ קל לשכוח — האינדקס חייב להתעדכן גם
  });
}
```

> ⚠️ שימו לב לשורה האחרונה. אם `roomCodes/{code}/adminId` לא מתעדכן, המנהל **הישן** נשאר עם הרשאת כתיבה על האינדקס הציבורי. זו הדליפה הכי קלה לפספס במודל הזה.

### ⭐ 14. חשבון לא פעיל שנה

**✅ ההחלטה למפרט הזה: לא עושים כלום אוטומטית.**

זה חדר מעונות עם 4 אנשים. מחיקה אוטומטית של חשבון שלא נכנס שנה תסיר משתמש שיצא לחופשת לימודים — ותשבור את היומן הכספי.

**מה כן מיישמים:**

1. `lastActiveAt` נכתב בכל התחברות — התשתית קיימת
2. בדף החברים, חבר שלא נכנס מעל 60 יום מסומן: `😴 לא נכנס מ-3 בינואר`
3. המנהל מקבל את המידע ומחליט **הוא** אם להסיר

```tsx
{daysSince(member.lastActiveAt) > 60 && (
  <span className="text-xs text-slate-500">
    😴 לא נכנס {formatRelative(member.lastActiveAt)}
  </span>
)}
```

**מה שנדחה במכוון:** מחיקה אוטומטית, מיילים אוטומטיים (דורש Cloud Functions + עלות), ארכוב אוטומטי של חדרים.

### 16. המשתמש משנה שם — הנתונים המשוכפלים מתיישנים

**✅ ההחלטה: fan-out update** לכל החדרים בכתיבה אטומית אחת. [קוד ב-04](./04-development-guide.md#35--שינוי-שם-משתמש--fan-out).

## ד. חדרים והצטרפות

### ⭐ 17. הצטרפות לחדר שלא קיים

**✅ ההחלטה:** קריאה מ-`roomCodes/{code}` לפני כל דבר אחר. שגיאה ברורה: *"קוד החדר אינו קיים"*.

**חוויית משתמש:**
- הקלט ממיר אוטומטית לאותיות גדולות ומסנן תווים לא חוקיים
- הקוד מוצג בקבוצות: `ABC 123`
- ולידציה מיידית: 6 תווים בדיוק, רק מהאלפבית המותר
- **הודעת השגיאה זהה** בין "קוד לא קיים" ל"קוד קיים אך אין הרשאה" — כדי לא לאפשר סריקה של קודי חדרים

---

### 18. בקשת הצטרפות כפולה

**✅ ההחלטה:** מפתח הבקשה הוא ה-`userId`, ולכן בקשה שנייה פשוט דורסת את הראשונה. אין כפילויות במבנה. ב-UI מוצג *"הבקשה שלכם ממתינה לאישור"* עם כפתור "בטל בקשה".

---

### 19. המשתמש הצטרף לחדר בזמן שהמנהל מחק אותו

**המצב:** קריאת `roomCodes` הצליחה, ובין לבין המנהל מחק את החדר.

**✅ ההחלטה:** הכתיבה תיכשל ב-Rules (`root.child('rooms/'+$code+'/metadata').exists()` נדרש). ההודעה: *"החדר אינו קיים עוד"*.

---

### 20. הצטרפות לחדר שכבר חבר בו

**✅ ההחלטה:** נחסם בשני מקומות — בדיקה מול `profile.rooms` בלקוח, וב-Rules (`!root.child(...members/auth.uid).exists()`). ההודעה: *"אתם כבר חברים בחדר הזה"* + כפתור מעבר לחדר.

## ה. מוצרים וכספים

### ⭐ 21. מוצר עם שם שכבר קיים

**המפרט ביקש אזהרה, לא חסימה** — וזה נכון: יכולים באמת להיות שני מוצרים בשם "חלב" (אחד לקפה ואחד לקורנפלקס).

**✅ ההחלטה: אזהרה לא-חוסמת בזמן ההקלדה.**

```tsx
function DuplicateItemWarning({ name }: { name: string }) {
  const { items } = useItems();
  const dup = items.find(
    (i) => i.nameLower === name.trim().toLowerCase() && i.status !== 'done'
  );
  if (!dup) return null;

  return (
    <div role="alert" className="rounded-lg bg-amber-50 p-3 text-sm text-amber-900">
      ⚠️ <b>{dup.name}</b> כבר ברשימה — דיווח {memberName(dup.reportedBy)},
      סטטוס: {statusLabel(dup.status)}.
      <button className="underline ms-1">הצג</button>
    </div>
  );
}
```

**ההשוואה על `nameLower`** — חסינה לרישיות ולרווחים מיותרים.

### ⭐ 22. סכום שלילי או לא תקין

**✅ ההחלטה: ארבעה רבדים.**

| רובד | מה נבדק | היכן |
|------|---------|------|
| קלט | `type="number" min="0.01" step="0.01" inputMode="decimal"` | `MoneyInput.tsx` |
| סכימה | `z.number().positive().max(100000)` | `schemas.ts` |
| המרה | `toAgorot()` מעגל למספר שלם | `money.ts` |
| **שרת** | `amount > 0 && amount <= 10000000 && amount % 1 === 0` | `database.rules.json` |

הרובד הרביעי הוא היחיד שבאמת מגן. השלושה הראשונים הם חוויית משתמש.

**מקרים נוספים שנחסמים:**

| קלט | תוצאה |
|-----|-------|
| `0` | "הסכום חייב להיות גדול מאפס" |
| `-50` | "הסכום חייב להיות חיובי" |
| `12.345` | מעוגל ל-`12.35` בהצגה, `1235` באגורות |
| `1e9` | "סכום גבוה מדי" |
| `""` / `abc` | "חובה להזין סכום" |
| חלוקה ל-0 משתתפים | "בחרו לפחות משתתף אחד" |

### 23. חלוקה שלא מסתכמת לסכום המלא

**המצב:** חלוקה מותאמת אישית — המשתמש הזין ₪10 + ₪10 מתוך ₪25.

**✅ ההחלטה:** בדיקה בזמן אמת בטופס, עם חיווי חי:

```
סה"כ הקנייה:  ₪25.00
חולק:         ₪20.00
נותר לחלק:    ₪5.00   ← 🔴 אדום, הכפתור מושבת
```

הכפתור "שמור" מושבת עד ש**נותר לחלק = ₪0.00 בדיוק**. בחלוקה שווה ובאחוזים — `lib/money.ts` מבטיח את זה מתמטית.

### 24. הקונה הוא היחיד ב-`splitBetween`

**המצב:** מישהו קנה משהו לעצמו בלבד.

**✅ ההחלטה:** לגיטימי לחלוטין — מותר. המאזן שלו: `+amount - amount = 0`. אין השפעה על אף אחד. מוצג ב-UI כ*"קנייה אישית"* כדי שלא ייראה כמו טעות.
