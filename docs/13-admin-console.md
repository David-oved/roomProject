# 13 · קונסולת המנהל — חוזה הנתונים

המסמך הזה מגדיר את **הממשק בין אפליקציית המשתמשים לקונסולת המנהל**.
הוא הרפרנס לכל מי שמפתח את צד הלקוח: אילו צמתים חדשים קיימים, מי כותב
לכל אחד, ומה האפליקציה צריכה לעשות איתם.

הוראות הפעלה, ארכיטקטורה והחלטות עיצוב של הקונסולה עצמה נמצאות ב-
[`admin/README.md`](../admin/README.md).

---

## מפת הצמתים החדשים

```
feedback/{feedbackId}          ← הלקוח כותב · הקונסולה קוראת
adminMessages/{uid}/{msgId}    ← הקונסולה כותבת · הלקוח קורא ומסמן נקרא
suspensions/{uid}              ← הקונסולה כותבת · הלקוח קורא את שלו
adminConsole/**                ← הקונסולה בלבד. הלקוח לא רואה ולא כותב
```

הכללים המלאים נמצאים ב-`database.rules.json`, בבלוקים שמסומנים בשמות
האלה. הקונסולה עצמה עובדת דרך Admin SDK ולכן **עוקפת** את הכללים — הם
קיימים כדי לתחום את הלקוח.

---

## 1 · משוב מהמשתמשים · `feedback/{id}`

הערוץ שדרכו משתמש מדווח תקלה, מבקש פיצ׳ר, שואל שאלה או מחמיא.

```jsonc
{
  "roomCode": "AB2K7Q",              // חדר שהמשתמש חבר פעיל בו
  "userId": "<auth.uid>",          // חייב להיות הכותב עצמו
  "type": "bug",                   // bug | feature | issue | question | compliment | other
  "subject": "לוח המחוונים לא נטען בנייד",   // 3–80 תווים
  "body": "כשאני פותח את האפליקציה…",        // עד 2000 תווים
  "createdAt": 1755772800000,
  "environment": {                 // רשות — מחרוזות קצרות בלבד
    "device": "iPhone 12",
    "browser": "Safari",
    "os": "iOS 16.2",
    "appVersion": "1.21.0"
  },
  "attachments": [                 // רשות — URL חייב להיות https
    { "name": "screenshot.jpg", "size": 125952, "url": "https://…" }
  ]
}
```

**כללים לצד הלקוח**

- כתיבה היא **יצירה בלבד**. אחרי ה-push אי אפשר לערוך או למחוק —
  הרשומה היא עדות המשתמש, והסטטוס שלי נשמר בנפרד.
- `userId` חייב להיות `auth.uid`, ו-`roomCode` חייב להיות חדר שבו
  המשתמש `active`.
- המשתמש יכול לקרוא **רק את הרשומות שהוא כתב**.
- `environment` כדאי למלא אוטומטית מ-`navigator.userAgent` ומ-
  `__APP_VERSION__`. זה מה שהופך דיווח "לא עובד" למשהו שאפשר לשחזר.

**מה שהמשתמש צריך לראות אחרי השליחה**

> „תודה, קיבלנו את המשוב. אם נצטרך פרטים נוספים או שיהיה עדכון,
> תגיע אליך הודעה מהמנהל.”

התשובה שלי מגיעה כהודעה רגילה ב-`adminMessages` (סעיף 2), עם
`relatedFeedback` בעותק ה-DM. אין צורך במסך נפרד לתשובות.

## 2 · הודעות ממנהל המערכת · `adminMessages/{uid}/{msgId}`

התיבה האישית של כל משתמש. משמשת לשלושה דברים: שידור כללי, הודעה אישית,
ותשובה למשוב.

```jsonc
{
  "title": "תחזוקה הלילה",
  "body": "בין 02:00 ל-04:00 המערכת תהיה בתחזוקה…",
  "kind": "warning",               // info | success | warning | error | maintenance
  "cta": { "text": "פרטים", "url": "https://…" },   // רשות
  "sentAt": 1755772800000,
  "readAt": null,                  // ← הלקוח כותב
  "clickedAt": null                // ← הלקוח כותב (בלחיצה על ה-CTA)
}
```

**כללים לצד הלקוח**

- קריאה: `auth.uid === $uid` בלבד.
- כתיבה: **רק** `readAt` ו-`clickedAt`. `title`, `body` ו-`sentAt`
  קפואים בתנאי הכתיבה עצמו — ניסיון לשנות אותם נדחה על ידי הכללים.
- `readAt` נכתב כשההודעה נפתחה בפועל, לא כשהיא הגיעה. הקונסולה מציגה
  "זמן עד קריאה", ומספר שנרשם מוקדם מדי הופך את המדד לחסר ערך.
- מונה "לא נקראו" = מספר הרשומות עם `readAt === null`.

**מה כדאי לבנות בלקוח**

1. באנר/מודאל שמופיע כשיש הודעה לא נקראה, לפי `kind`
   (אזהרה בכתום, תחזוקה בכתום, מידע בכחול).
2. מסך „הודעות ממנהל המערכת” בהגדרות — היסטוריה מלאה.
3. התראת פוש: מומלץ לחבר את זה ל-`outbox` הקיים אם רוצים דחיפה מיידית;
   בלי זה ההודעה מחכה לכניסה הבאה של המשתמש.

## 3 · השעיה · `suspensions/{uid}`

```jsonc
{ "at": 1755772800000, "reason": "שימוש לרעה בדיווחים" }
```

- קריאה: המשתמש עצמו בלבד. כתיבה מהלקוח: **אסורה לחלוטין**.
- כשהצומת קיים, האפליקציה צריכה לחסום את הכניסה ולהציג הסבר קצר עם
  אפשרות לפנות (משוב מסוג `issue`).
- ‼️ הדגל יושב בצומת נפרד ולא בתוך `users/{uid}` בכוונה: הלקוח כותב את
  `users/{uid}` ב-`set` מלא בהרשמה ובתיקון פרופיל, וכתיבה כזו הייתה
  מוחקת דגל שיושב באותו אובייקט — כלומר המושעה היה משחרר את עצמו.

## 4 · מרחב הקונסולה · `adminConsole/**`

סגור ללקוח לחלוטין (`.read: false`, `.write: false`). מתועד כאן כדי
שיהיה ברור מה יושב שם ולמה אין לגעת בו:

| צומת | תוכן |
|---|---|
| `feedbackState/{id}` | סטטוס, עדיפות, הערות פנימיות, תשובות וציר זמן לכל משוב |
| `messages/{id}` | ההודעות שיצאו + מעקב מסירה/קריאה/לחיצה |
| `templates/{id}` | תבניות הודעה |
| `dm/{uid}/{id}` | שיחות אישיות מולי |
| `alertConfig`, `alertState` | טריגרים, שעות שקט, מה כבר ראיתי |
| `auditLog/{id}` | כל פעולה שהקונסולה ביצעה על הנתונים |
| `backups/{id}` | גיבוי צומת לפני פעולה הרסנית |
| `suspensions/{uid}` | עותק ביקורת של השעיות |
| `archivedRooms/{code}` | חדרים שאורכבו + סיבה |

**הפרדה שחשוב להבין:** `feedback/{id}` היא עדות המשתמש ואינה משתנה אף
פעם; `adminConsole/feedbackState/{id}` הוא מה שאני עשיתי עם זה. לו הייתי
מעדכן סטטוס בתוך אותה רשומה, כל שינוי שלי היה נראה כאילו המשתמש כתב
אותו — וגם היה מחייב לתת ללקוח הרשאת כתיבה על שדות שהם שלי בלבד.

## 5 · פעולות שהקונסולה מבצעת על הנתונים הקיימים

הקונסולה כותבת גם לצמתים הרגילים של האפליקציה. כל כתיבה כזו נרשמת
ב-`auditLog`, ולפני פעולה הרסנית נשמר גיבוי.

| פעולה | מה משתנה בפועל |
|---|---|
| אישור / דחיית קנייה | `rooms/{code}/purchases/{id}/status` + חישוב מחדש של `balances` |
| אישור / דחיית הצטרפות | `members/{uid}` נוצר, `pendingRequests/{uid}/status` מתעדכן |
| הסרת חבר | `members/{uid}/status = removed` (לא מחיקה) |
| העברת ניהול | `metadata/adminId`, `members/*/role`, `roomCodes/{code}/adminId` |
| סנכרון כפוי | חישוב מחדש של `balances` מיומן הקניות |
| איפוס מאזנים | קניות `approved` → `settled`. הקניות נשארות |
| ארכוב חדר | `metadata/archivedAt`. שום ענף לא נמחק |
| שידור לחדר | `announcements` חדש עם `fromSystemAdmin: true` |

**שדה שהלקוח צריך להכיר:** `announcements/{id}/fromSystemAdmin === true`
מסמן שידור שהגיע ממני ולא ממנהל החדר. כדאי להציג אותו אחרת (למשל
תג „מנהל המערכת”), כדי שחברי החדר לא יחשבו שמנהל החדר כתב את זה.

וכן `metadata/archivedAt` — כשהוא קיים, האפליקציה צריכה להציג את החדר
כקריאה-בלבד ולא לאפשר דיווחים וקניות חדשות.

## 6 · מה כבר קיים בצד הלקוח

כל הסעיפים למעלה ממומשים באפליקציה. המפה, למי שמחפש איפה לגעת:

| מה | איפה |
|---|---|
| שליחת משוב (כולל איסוף `environment` אוטומטי) | `src/services/feedbackService.ts` · `src/pages/FeedbackPage.tsx` |
| תיבת ההודעות + סימון `readAt` / `clickedAt` | `src/services/adminMessageService.ts` · `src/pages/AdminMessagesPage.tsx` |
| באנר הודעה חדשה במסך הבית | `src/components/system/AdminMessageBanner.tsx` |
| חסימת משתמש + מסך ערעור | `src/hooks/useAdminMessages.ts` (`useSuspension`) · `src/pages/SuspendedPage.tsx` · `RequireAuth` |
| חדר בארכיון: באנר + חסימת כתיבה | `src/components/system/RoomArchivedBanner.tsx` · `src/services/guard.ts` (`assertRoomWritable`) |
| תג "מנהל המערכת" על שידור | `src/pages/AnnouncementsPage.tsx` |
| דופק `lastActiveAt` בכל פתיחת אפליקציה | `src/store/AuthContext.tsx` |

### הערות מימוש ששווה להכיר

**המשוב הוא "שגר ושכח" מבחינת הלקוח.** הכללים מתירים קריאה של פנייה
בודדת אך לא סריקה של האוסף, ולכן "הפניות ששלחתי" נשען על רשימה מקומית
(`src/lib/prefs.ts`). מחיקת נתוני הדפדפן מוחקת את הרשימה — הפנייה עצמה
נשארת אצל המנהל. זה המחיר, והוא זול מלפתוח את האוסף לקריאה.

**חסימת הכתיבה בחדר מאורכב עוברת דרך שכבת ה-services**, בדיוק כמו מצב
אופליין: `RoomProvider` דוחף את המצב ל-`guard.ts`, וכל פונקציית כתיבה
קוראת ל-`assertRoomWritable(code, …)` מיד אחרי `assertOnline(…)`. הצ׳אט
נשאר פתוח בכוונה — חדר שהועבר לארכיון הוא בדיוק המצב שבו השותפים
צריכים לדבר על מה שקרה.

**החסימה נאכפת בשרת, לא במסך.** `RequireAuth` מציג את מסך החסימה, אבל
מה שבאמת חוסם הוא שהקונסולה מסירה גישה בצד הנתונים. המסך קיים כדי
להסביר — ולתת דרך לערער דרך ערוץ המשוב הרגיל.

## 7 · פיתוח ובדיקה מקומית

```bash
npm run emu        # אמולטורים (Auth + RTDB) עם הכללים האמיתיים
npm run emu:seed   # 14 משתמשים, 5 חדרים, משוב, הודעות, חדר בארכיון ומשתמש חסום
npm run dev        # האפליקציה, מול האמולטור (VITE_USE_EMULATORS=true)
```

לחיבור קונסולת הניהול לאותם נתונים — בלי מפתח ייצור:

```bash
FIREBASE_DATABASE_EMULATOR_HOST=127.0.0.1:9000 \
GCLOUD_PROJECT=<project-id> npm run admin:server
```

הזריעה יוצרת משתמשי Authentication אמיתיים, כך שאפשר להתחבר דרך מסך
ההתחברות: `david@example.com` / `roommate123` (חבר בשני חדרים, יש לו
הודעות ופנייה שנענתה), ו-`adi@example.com` / `roommate123` (חסום).

בדיקות:

```bash
npm test              # יחידה — כולל ולידציית המשוב ושומר הארכיון
npm run test:rules    # כללי האבטחה מול אמולטור, כולל הצמתים כאן
```

## 8 · מלכודת שכבר נפלנו בה

קודי החדר בנתוני ההדגמה נבנו בתחילה בני ארבעה תווים (`AB12`), בעוד
שהמערכת מייצרת קודים בני שישה. בקונסולה הכול נראה תקין — היא קוראת
דרך Admin SDK ולכן עוקפת כללים — אבל **כל כתיבה מהאפליקציה לחדרים
האלה נדחתה** ב-`PERMISSION_DENIED`, כי `roomCode` נבדק מול
`/^[A-Z0-9]{6}$/`.

המסקנה שנשארה בקוד: נתוני הדגמה שנקראים רק דרך Admin SDK אינם מוכיחים
כלום על הלקוח. הבדיקה `tests/admin/adminConsole.test.ts → נתוני ההדגמה`
נועלת את זה — היא מוודאת שכל קוד חדר בנתוני ההדגמה תקף גם לפי הכללים
וגם לפי מחולל הקודים.
